# 架构设计

## 总览

LocalFlow AI 采用 **Port & Adapter（六边形架构）**，核心思想是：

> 让「变的部分」（具体实现）与「不变的部分」（领域模型）解耦。

这样 DSH 更新、推理后端更换，都只影响 adapters 层，不影响核心业务逻辑。

## 四层架构

```
┌──────────────────────────────────────────────────────────┐
│                    UI 桌面层 (Electron)                  │
│  模型选择 · 对话 · 工作流画布 · 硬件监控 · 回溯时间轴    │
└──────────────────────────┬───────────────────────────────┘
                           │ HTTP / IPC
┌──────────────────────────▼───────────────────────────────┐
│                     API 层 (FastAPI)                     │
│  models · chat · hardware · wizard · sessions · plugins  │
└──────────────────────────┬───────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│                    核心层 (core/)                        │
│  LocalFlowApp · SessionManager · PluginManager · Wizard  │
│  （只依赖 ports 抽象，不依赖具体实现）                    │
└──────────────────────────┬───────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│              Ports 稳定领域接口层 (ports/)                │
│  engine · cache · event · scheduler · hardware           │
│  （契约层，稳定不变）                                     │
└──────────────────────────┬───────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│            Adapters 具体实现层 (adapters/)               │
│  Ollama · OpenAI · SQLite Cache · SQLite Event           │
│  LLMSplit Scheduler · System Hardware                   │
│  （变更层，DSH 更新时只换这里）                            │
└──────────────────────────────────────────────────────────┘
```

## 设计原则

### 1. 面向接口编程，不面向实现
所有业务逻辑通过 `ports/` 的抽象接口交互，`LocalFlowApp` 在入口处统一装配 adapter。

### 2. Schema 稳定优先
跨版本的粘合数据（缓存 Key、Event、子任务协议）使用本地领域模型命名，绝不硬编码 DSH 或后端的私有字段。

### 3. 可插拔优先
新能力优先通过插件或 feature flag 引入，可灰度、可摘除，与主链路解耦。

### 4. 小步快跑
MVP 只做最小闭环，后续能力通过 adapter 和插件逐步叠加。

## 依赖方向

```
UI → API → Core → Ports ← Adapters
```

**依赖永远指向抽象（Ports）**，从不反向指向具体实现。

## 数据流（一次聊天请求）

```
用户消息
  → API /chat
    → SessionManager.chat()
      → 记录 user_message 事件 (EventStore)
      → 加载历史 (EventStore)
      → 检查缓存 (CacheEngine)  ← 命中则直接返回
      → 调用引擎 (LLMEngine)
      → 记录 assistant_message 事件 (EventStore)
      → 写入缓存 (CacheEngine)
  ← 返回结果
```

## 为什么不直接用 DSH

- DSH 是 Agent 调度框架，不做 GPU 显存管理
- 不做模型下载、硬件检测、自动量化
- 协议可能变化，fork 后维护成本高
- 我们需要完整掌控硬件层到 UI 层的全链路体验

通过 Port & Adapter，我们既能借鉴 DSH 的架构思想，又保持了完全的自主权。
