## 〇 · 设计之初就为 DSH 迭代留的「窗口」

**核心原则：追踪 DSH 的「抽象 / 契约」，而非「实现」**

同步发生在概念与接口语义层，不是逐行对齐源码。把 DSH 的四大能力视为可替换的实现（adapter），而本地稳定守住自己的领域接口（port）。DSH 每一次迭代 → 只更新对应 adapter，无需动核心与持久化层。

### 为什么「同步 DSH」成立、又必须这么做

「复刻 DSH 核心能力」意味着本地实现与 DSH 愿景同源演进。但若逐行绑定 DSH 源码，DSH 更新会直接冲击本地持久化 schema、缓存 Key、事件协议，导致维护成本失控。所以关键在于：**让「变的部分」（DSH 具体实现）与「不变的部分」（本地领域模型）解耦**。

### 落实到工程骨架的四个窗口

```
┌─────────────────────────────────────────────────┐
│  稳定层（不变）— 领域契约 (ports/)              │
│  • 引擎接口   • 事件溯源接口                    │
│  • 缓存接口   • 子任务调度接口                  │
└───────────────────────┬─────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────┐
│  变更层（随 DSH 更新）— 实现 (adapters/)        │
│  • DSH 参考实现 vN   • DSH 参考实现 vN+1        │
│  • 自研替代实现                                 │
└───────────────────────┬─────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────┐
│  跨版本粘合数据（稳定）                         │
│  • 缓存 Key（规范化）                           │
│  • Event Schema（稳定领域模型）                 │
│  • dsh_compat 兼容矩阵                          │
└─────────────────────────────────────────────────┘
```

### 机制 S · 同步窗口落地（骨架期完成）

- [ ] **S1 目录即契约：预留 `ports/` 与 `adapters/` 两层**
  领域接口集中在 `ports`（引擎 / 事件溯源 / 缓存 / 子任务调度）；DSH 参考实现与自研替代都放 `adapters`，互不污染。
  `标签：骨干`

- [ ] **S2 建立 `dsh_compat` 兼容矩阵文档**
  记录 DSH 各版本 → 本地各能力「对齐状态」（已对齐 / 需评估 / 差异），作为每次同步的对照清单。
  `标签：文档`

- [ ] **S3 CI 监控 DSH release**
  定时检测 DSH 仓库新 tag，触发「对齐评估」issue 模板，避免遗漏上游更新。
  `标签：CI`

- [ ] **S4 Schema 稳定优先：禁止硬编码 DSH 私有字段**
  缓存 Key、Event、子任务协议的持久化定义用「稳定的本地领域模型」，DSH 内部字段只留 adapter 内。
  `标签：高优`

- [ ] **S5 新能力一律走插件或 feature flag**
  与主链路解耦，可灰度、可摘除——满足「同步迭代后随时回退」。
  `标签：架构`

## 贯穿全局的精益原则

- 第一版不承诺命中率数字，用真实数据迭代
- 后端与 UI 解耦，命令行先演示价值
- 插件化先行，后续高级能力可插拔、可回退
- 本地模型聚焦主力场景，避免贪多
- 每阶段结束发一次版本或内容，保持开源热度
- 进阶能力（L3/L4、多 API 聚合、难度路由）明确延后，各自独立立项
